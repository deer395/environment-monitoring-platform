# DECISION_LOG

## 使用说明

* 出现以下情况时，应新增决策记录：

  * 项目目标、范围或使用场景发生实质变化；
  * 数据流程、质控规则、统计口径或报告结构发生变化；
  * 多个可选方案经过比较后形成明确结论；
  * 某项方案会持续影响后续代码、测试、文档或项目展示；
  * 原有方案被明确推翻、替代或停止使用。

* 以下内容只应更新 `CURRENT_STATUS.md`，不应新增决策：

  * 当前分支、提交哈希和标签；
  * 一次测试结果；
  * 当前报错或临时缺陷；
  * 最近完成的任务；
  * 某个文件是否已修改；
  * 尚未形成长期影响的一次性操作；
  * 下一步执行顺序发生的小幅调整。

* 决策被推翻时：

  * 不删除原决策；
  * 将原决策状态改为“已替代”或“已否决”；
  * 在原决策中注明替代它的新决策编号；
  * 在新决策中注明其替代的旧决策编号；
  * 保留原决策的背景、理由和问题表现。

* 不得删除仍有解释价值的历史决策。已经失败的方案如果能够说明问题来源、项目迭代逻辑或技术取舍，应继续保留，供后续维护和面试复盘使用。

  * 用户明确表示，当前主要目的是形成一段有说服力的项目经历，而不是立即开发完整商业产品。

### D-002 核心分析和报告采用本地确定性规则

* 状态：已确认
* 决策时间：本长对话阶段内，准确日期待确认
* 背景：

  * 曾讨论过使用大模型 API 对报告进行生成或润色；
  * 当前报告曾出现方向识别和阶段判断错误。
* 需要解决的问题：

  * 报告事实应由本地算法还是大模型生成；
  * 如何保证数字、月份、方向和结论可复现。
* 可选方案：

  * 完全由大模型生成报告；
  * 本地算法生成事实，大模型负责润色；
  * 完全采用本地确定性规则；
  * 当前使用本地规则，未来再讨论可选润色层。
* 最终采用方案：

  * 核心数据计算、事实提取和单变量报告使用本地确定性规则；
  * 当前不接入大模型 API。
* 采用理由：

  * 如果结构化事实错误，大模型只会将错误表达得更自然；
  * 本地规则更容易测试、复现和追溯；
  * API 会增加密钥、网络、成本、隐私、失败降级和数字保护等额外复杂度；
  * 当前求职项目不需要依赖大模型才能成立。
* 未采用方案及原因：

  * 完全由大模型生成：无法保证数字和事实稳定；
  * 当前立即增加润色层：会扩大范围，但不能解决底层识别错误。
* 依据：

  * 多轮报告检查表明，主要问题来自阶段识别而非单纯措辞；
  * 用户确认当前交接文件中不保留大模型润色作为既定路线。
* 影响范围：

  * 报告架构；
  * 数据安全；
  * 测试方式；
  * 部署复杂度；
  * 项目面试表述。
* 风险与代价：

  * 本地文本可能具有一定模板感；
  * 复杂语言表达能力受规则范围限制。
* 可否逆转：

  * 可以。
* 重新评估条件：

  * 用户未来明确提出需要语言润色；
  * 本地事实层已经稳定；
  * 能建立数字保护、失败降级和可关闭机制。
* 与其他决策的关系：

  * 与 D-006、D-010、D-012 和 D-013 共同构成确定性报告框架。

### D-003 自动质控与人工复核结合，最终分析统一使用 final_qc_data

* 状态：已确认
* 决策时间：本长对话阶段内，准确日期待确认
* 背景：

  * 自动异常规则可能产生误报；
  * 完全人工处理效率低；
  * 项目需要保留质控过程的可追溯性。
* 需要解决的问题：

  * 哪些记录由系统自动处理；
  * 哪些记录需要人工决定；
  * 后续统计使用哪个数据版本。
* 可选方案：

  * 所有候选异常自动删除；
  * 只提供人工清洗；
  * 自动处理确定性无效值，候选异常交由人工复核；
  * 统计直接使用自动质控结果。
* 最终采用方案：

  * 传感器零值和硬范围外数据由自动规则处理；
  * Hampel 和连续恒定值只生成候选；
  * 人工决定候选点和普通点的保留、删除或恢复；
  * 最终统计、绘图和报告统一使用 `final_qc_data`；
  * 全过程写入最终质控日志。
* 采用理由：

  * 自动规则提高效率；
  * 人工复核降低误删风险；
  * `final_qc_data` 能保证所有后续结果使用同一数据基线；
  * 日志能够支持追溯。
* 未采用方案及原因：

  * 候选异常全部自动删除：误删风险较高；
  * 完全人工清洗：效率低；
  * 直接使用自动质控结果：无法反映人工确认。
* 依据：

  * 项目现有流程和报告结构；
  * 用户对人工确认后再进入计算的要求。
* 影响范围：

  * 质控模块；
  * 人工复核界面；
  * 重采样；
  * 统计；
  * 图件；
  * Word 和 Excel 输出；
  * 日志。
* 风险与代价：

  * 人工复核需要额外操作；
  * 结果会受到人工判断影响；
  * 参数变化后需要重新确认。
* 可否逆转：

  * 可以，但属于核心架构变更。
* 重新评估条件：

  * 出现可靠性更高且经过验证的全自动规则；
  * 实际使用场景不再允许人工参与；
  * 质控业务规则发生变化。
* 与其他决策的关系：

  * 是所有报告和统计决策的前置条件；
  * 与 D-002 的可复现性要求一致。

### D-004 固定支持九个变量并通过变量注册表统一管理

* 状态：已确认
* 决策时间：本长对话阶段内，准确日期待确认
* 背景：

  * 早期代码中存在变量名称、单位和参数硬编码；
  * 项目需要支持多个变量使用同一流程。
* 需要解决的问题：

  * 当前需要支持哪些变量；
  * 变量名称、单位、范围和质控参数应在哪里维护。
* 可选方案：

  * 只支持少量核心变量；
  * 每个变量单独维护代码；
  * 固定九个变量，并通过变量注册表集中管理；
  * 构建完全动态、无限制的变量系统。
* 最终采用方案：

  * 固定启用九个变量，不再删减：

    1. 水深；
    2. 温度；
    3. 盐度；
    4. 溶解氧；
    5. 化学需氧量；
    6. 生化需氧量；
    7. 硝酸盐；
    8. 叶绿素；
    9. 多环芳烃。

  * 九个变量覆盖当前真实项目需要；
  * 集中注册可以减少页面、图件、表格和报告之间的不一致；
  * 不需要为求职项目继续扩展无限变量系统。
* 未采用方案及原因：

  * 继续删减变量：用户明确确认九个变量均保留；
  * 每个变量独立实现：会造成重复和硬编码；
  * 无限动态变量系统：当前没有必要。
* 依据：

  * 用户明确确认变量固定为九个，不再删减；
  * 项目已有变量注册表结构。
* 影响范围：

  * 页面选择；
  * 数据加载；
  * 质控参数；
  * 图件；
  * Excel；
  * Word；
  * 测试。
* 风险与代价：

  * 新增第十个变量仍需要注册配置；
  * 不同设备或站点可能需要重新核验参数。
* 可否逆转：

  * 可以。
* 重新评估条件：

  * 出现明确的新变量需求；
  * 某变量被业务正式取消；
  * 项目转为更通用的平台。
* 与其他决策的关系：

  * 与 D-013 的禁止变量专用分支共同保证通用性。

### D-007 报告内容按 hourly、intraday、monthly 三个尺度组织

* 状态：已确认
* 决策时间：本长对话阶段内，准确日期待确认
* 背景：

  * 固定模板难以区分不同时间尺度的事实；
  * 小时极值、日内周期和月际变化容易混在同一段。
* 需要解决的问题：

  * 报告事实如何分层；
  * 不同尺度的统计信息如何避免重复。
* 可选方案：

  * 全部事实写在一个综合段落；
  * 按图件逐段说明；
  * 按 `hourly → intraday → monthly` 三个尺度独立生成。

  * 时间变化综合分析固定分为：

    * `hourly`；
    * `intraday`；
    * `monthly`。
  * 各尺度只描述自身负责的事实。
* 采用理由：

  * 能够明确区分主体范围、周期、日变化和月际阶段；
  * 结构统一；
  * 便于测试和维护；
  * 不需要通过随机句式制造差异。
* 未采用方案及原因：

  * 单一综合段落：事实容易混杂；
  * 随机变化句式：不能提高事实准确性。
* 依据：

  * 用户明确要求综合分析采用该顺序；
  * 最新报告均已采用。
* 影响范围：

  * 报告上下文；
  * 叙述生成；
  * Word 排版；
  * 测试。
* 风险与代价：

  * 某些变量在部分尺度上特征不明显，文字可能较通用；
  * 需要控制不同段落之间的重复。
* 可否逆转：

  * 可以，但属于报告长期结构变更。
* 重新评估条件：

  * 报告使用场景要求另一种正式模板。
* 与其他决策的关系：

  * 替代 D-006；
  * 与 D-009、D-010 和 D-012 配套。

### D-011 月平均采用通用多阶段方向识别

### D-012 结论基于主要全过程并优先保留强周期特征

### D-023 业务内核版本、UI 阶段与报告模板版本分别管理

* 状态：已确认
* 决策时间：2026 年 7 月 23 日
* 背景：

  * 早期页面曾使用单一版本名称描述整个产品；

  * 单变量和站点 Word 模板也有独立变化；
  * 单一版本号会让用户误以为业务算法已经升级，或把历史业务标签误认为当前 Git 构建标签。
* 需要解决的问题：

  * 如何准确区分业务算法、UI、报告模板和代码构建；
  * 报告应显示什么版本信息；
  * 如何避免多文件分别硬编码版本号；
  * 模板更新后如何防止继续下载旧报告缓存。
* 可选方案：

  * 页面、算法和报告全部使用 V5.4；
  * 所有地方继续统一显示 V4.2；
  * 运行时读取当前 Git 分支或 Git 标签作为唯一版本；
  * 分离业务内核、业务基线、UI 阶段和报告模板版本，并集中维护。
* 最终采用方案：

  * 业务内核版本保持 V4.2，V5.4 表示 UI 与报告模板演进阶段，不表示业务算法升级；
  * 业务基线标签与当前构建信息概念分离；
  * 单变量 Word 和站点综合 Word 使用独立模板版本；
  * 版本常量由统一版本模块 `src/version.py` 集中管理；
  * 报告展示“业务内核版本”和“业务基线标签”，且不得强制依赖运行时 Git 命令；
  * 模板版本变化时，相应 Word 缓存必须失效，但不得清除 QC、`final_qc_data` 或无关导出结果。
* 采用理由：

  * 准确表达算法和界面变化，防止将 UI 更新误解为统计或质控算法更新；
  * 减少旧版本硬编码，提高 Word 报告可追溯性；
  * 支持无 Git 部署环境，并让模板更新可靠触发缓存失效。
* 未采用方案及原因：

  * 全部写为 V5.4：会错误表达业务算法变化；
  * 全部写为 V4.2：无法追踪 UI 和模板演进；
  * 只读取运行时 Git：无 Git 或部署环境中不可靠，也不能准确表示业务语义；
  * 多文件分别硬编码：容易再次出现页面、报告和文档版本不一致。
* 依据：

  * 页面 UI 和报告样式已独立演进；
  * V5.4 中业务逻辑和 widget key 未改变；
  * 报告旧版本字段与旧缓存问题已实际暴露并修复；
  * 单变量和站点 Word 已建立模板版本失效机制。
* 影响范围：

  * 页面版本表达、Word 报告元数据、单变量与站点 Word 缓存、发布、部署和后续版本文档。
* 风险与代价：

  * 版本概念增加，需要文档明确区分；
  * 更新模板时必须同步更新对应模板版本；
  * 忘记更新统一版本模块可能导致缓存不失效；
  * UI 版本仍需通过发布记录管理。
* 可否逆转：

  * 可以重新设计版本体系；
  * 在形成新的统一版本体系前，业务内核版本、UI 阶段和报告模板版本不得重新混用。
* 重新评估条件：

  * 业务算法真正升级到新版本；
  * 项目建立正式构建号、发布流水线或语义化版本；
  * UI 与业务内核改为统一发布周期；
  * 报告模板转为外部模板管理。
* 与其他决策的关系：

### D-024 高保真 UI 以 P0/P1 为发布门槛并在 RC1 后停止开放式美化

* 状态：已确认
* 决策时间：2026 年 7 月 23 日
* 背景：

  * 页面经过多轮结构、层级、图表、报告和视觉修正；
  * 继续开放式美化容易陷入字号、间距、圆角和风格的无边界调整；
  * 项目主要业务闭环已经完成，下一阶段价值来自部署、其他电脑运行、完整站点任务和用户试用。
* 需要解决的问题：

  * 什么条件下停止 UI 修改；
  * P2 视觉事项是否阻塞发布；
  * V5.4 应冻结为候选版还是继续无限优化；
  * 如何将开发主线切换到部署和交付。
* 可选方案：

  * 继续根据所有视觉意见逐项修改；
  * 只要仍有 P2 就不冻结；
  * 以无 P0/P1 为发布门槛，P2 进入后续待办；
  * 不做验收，直接宣布正式稳定版本。
* 最终采用方案：

  * UI/UX 最终验收只将 P0 和 P1 作为当前发布阻断项；
  * 没有 P0/P1 后，冻结 V5.4 为发布候选版 RC1，P2 不阻塞 RC1；
  * RC1 不等同于正式稳定版；
  * 不再继续开放式调整布局、配色、字号、圆角和一般视觉细节；
  * 后续主线转向部署、端到端交付和真实用户验证；
  * 只有真实使用暴露 P0/P1，或出现明确新业务需求时，才重新打开相关 UI 或功能修改。
* 采用理由：

  * 防止无边界美化并保持投入产出合理；
  * 当前页面已达到企业级内部工作台候选标准；
  * 部署和真实使用更能验证产品价值；
  * RC 机制允许在正式稳定版前继续发现问题。
* 未采用方案及原因：

  * 继续修改全部 P2：收益有限且会推迟真实试用；
  * P2 全部清零后才发布：没有明确终点；
  * 直接宣布正式稳定版：尚缺其他电脑运行、九变量站点端到端和实际用户验证。
* 依据：

  * 最终 UI/UX 验收无 P0/P1；
  * 顶部任务栏、报告格式、版本、缓存和图表问题已完成修复；
  * RC1 已冻结，尚需部署和完整站点端到端验证。
* 影响范围：

  * UI 开发边界、发布候选标准与 P0/P1/P2 问题管理、部署优先级、用户试用和正式稳定版判定。
* 风险与代价：

  * 部分 P2 视觉或响应式事项会保留；
  * Streamlit 原生界面痕迹仍可能存在；
  * RC1 尚不能等同于正式生产版本；
  * 部署和真实数据仍可能暴露新问题。
* 可否逆转：

  * 可以；
  * 但只有明确 P0/P1、真实用户反馈或新业务需求才应重新打开主线；
  * 不应仅因一般审美偏好重新进入无边界调整。
* 重新评估条件：

  * 其他电脑无法正常运行；
  * 九变量完整任务出现阻断；
  * 综合 Excel 或 Word 生成失败；
  * 用户试用发现关键流程难以理解；
  * 项目决定升级为正式长期产品；
  * 出现明确的新产品设计目标。
* 与其他决策的关系：

  * 落实 D-001 的项目范围控制；
  * 延续 D-014 的停止无边界算法扩展原则；
  * 完成 D-019 的页面美化阶段并进入部署主线；
  * 基于 D-022 的分支隔离和 D-023 的版本体系；
  * 不改变 D-021 的月际算法冻结结论。
